# Personal Assistant — Architecture and Roadmap

High-level context for the PA monorepo. Specs and issues are written from this document. It sets direction and boundaries; it does not prescribe implementation.

## Purpose

A personal assistant that remembers the world around its owner (Coy): people, meetings, emails, chats, calendar, and notes. It answers questions the way a good human assistant would: with attribution, in time order, and with awareness of what is still open.

Representative questions for the work PA:

- "What's happened with the web search feature?" Expected shape: *"About a month ago you floated it in the weekly team meeting. Jay agreed and said he'd follow up with security. Two weeks ago Cam asked about it and you said you were waiting on Jay. Since then you've mentioned it in the user group, but that's as far as it's gotten."*
- "Did Cam change his mind since last week on open-source model hosting?"
- "What have I said to whom about an API key feature, and how has my stance changed?"
- "What's on my plate today, and what am I waiting on from other people?"

Representative questions for the home PA:

- "When could we fit the kids' swim lessons in, given my wife's late shifts and the birthday parties coming up?"
- "Did the contractor ever send the revised quote he promised?"
- "What did I write about the soccer league over the last month?"

The owner chats with the PA from phone and Mac, and receives a morning brief without asking.

## Two instances, one codebase

The PA runs as two fully separate instances built from this one codebase. **No data is shared between them**: work content never reaches the home PA, and personal content never reaches the work PA.

| | Home PA | Work PA |
|---|---|---|
| Hosting | Isolated VM on the owner's Ubuntu devbox, over Tailscale | Employer's Databricks workspace on AWS (Bridgestone) |
| Sources | Gmail, iCloud Calendar, Obsidian vault, assistant chat | Outlook mail and calendar, Teams chats, Teams meetings, Anarlog, assistant chat |
| Capture | Scheduled pulls by collectors on the devbox | Power Automate flows (running as the owner) landing raw payloads in a tenant landing zone; the Mac uploads Anarlog transcripts only |
| Storage | Local files and databases on the devbox | Delta tables, Unity Catalog Volumes, Lakebase |
| Jobs | systemd timers | Databricks Jobs / Lakeflow pipelines |
| Models | Claude on the owner's subscription | Databricks-served Claude through Unity Gateway's Anthropic-compatible endpoint |
| Harness | Claude Code (shared agent project) | Claude Code (shared agent project) |
| Chat | Remote Control (claude.ai/code, Claude app) | Omnigent (workspace web and mobile); fallback: Agent SDK app with a chat page |
| Brief delivery | Push channel to phone | Teams message via Power Automate |

The home PA is built first. The work instance follows once the owner starts at Bridgestone. Work-specific constraints and open questions live in the separate handoff document *Work PA on Databricks*.

### What is shared and what is swapped

**Shared core** (identical in both instances):

- **Core Python package:**
  - episode envelope, `episode_id` and `content_hash` rules, and per-source normalizers
  - L0 ingest semantics: append-only, idempotent, quarantine for malformed input
  - extraction prompts, output schemas, and the extraction pipeline
  - graph schema and the domain query layer
  - wiki page generation
- **PA MCP server:** exposes the domain queries over the claims graph to the harness, with a schema tool and a read-only query tool beside them (from v0.12).
- **Agent project:** a Claude Code project directory, and the entire harness configuration. It contains:
  - `CLAUDE.md` (persona and instructions)
  - `.claude/skills/` (morning brief, timelines, open loops, …)
  - the MCP configuration
  - `settings.json` (permissions)
  - hooks (for example, session transcripts to L0)
  - The Agent SDK reads the same project configuration, so scheduled and fallback runs behave like interactive ones.
- **Eval harness, synthetic corpus, and eval sets.**

**Swapped per instance** (behind small interfaces or environment configuration):

- **Storage adapter:** L0, extraction cache, wiki, and graph persistence, plus the read-only file view of L0 and the wiki that the assistant reads.
- **Job runtime:** scheduling and orchestration.
- **Extraction model client:** "prompt plus schema in, structured output out." One backend uses subscription CLIs (`claude -p`, Codex); the other uses Databricks HTTP endpoints. This keeps the pipeline provider-neutral.
- **Capture:** home collectors (Python) vs. work landing-zone readers. Power Automate flow definitions are exported into the repo for versioning.
- **Harness environment:** model auth and endpoint, chat surface, and push channel.

Two rules keep the abstraction honest:

1. **Abstract at the domain level, not the database level.** The assistant calls domain queries such as `timeline(topic)`, `statements(who, topic, since)`, and `open_loops(who)` through the PA MCP server. For questions they don't cover, the same server offers a read-only `query` tool in its engine's language. Its `schema` tool returns the schema, with the domain queries' own text as examples, so nothing engine-specific is written into the agent project. Each storage adapter implements these in its own engine. Evidence (L0 episodes) and L1 wiki pages are read as files: each storage adapter presents them at a read-only path. If a work session can't reach files, the work adapter adds an MCP read path; that is an adapter concern, not a change to the agent project.
2. **Build seams, not speculative adapters.** Define each interface when the home PA first needs it, and implement only the home adapter. The work adapters are built in the work milestones, and the shared eval set proves parity.

## Principles

1. **L0 is the only source of truth.** Raw episodes are immutable and append-only. Every other layer is derived and rebuildable from L0. Corrections are new episodes, never edits.
2. **Derived layers are drafts.** Schemas, prompts, and page structures are expected to be wrong at first. A rebuild is the fix, so rebuilds must stay cheap. Never hand-edit derived layers: fix the extractor, or add an episode.
3. **Deterministic first.** Who, when, where, and to whom come from source metadata (senders, recipients, attendees, speaker labels, timestamps), not from an LLM. LLMs extract only meaning: topics, statement types, stances, commitments.
4. **Precompute the index, not the answer.** Derived layers exist to find and order the right evidence. The model reads the original passages at query time and writes the answer.
5. **Provenance everywhere.** Every derived item points back to the episode (and the span within it) that it came from. Answers cite their sources.
6. **The store is the product; the harness is configuration.** All PA behavior lives in the store, the PA MCP server, and the agent project. The harness itself contains no PA code.
7. **Contain untrusted content.** Raw source text is untrusted, since anyone can send an email. The fences sit at the VM boundary, not inside the session: the store is mounted read-only, the VM's network reach is set by its tailnet rules and the host firewall, and its only write path back is its inbox directory. Inside the VM the assistant has its normal tools. No fence relies on an approval prompt, since the chat client sets the permission mode.
8. **Read-only toward the world.** The PA reads and remembers. Its outputs are messages to the owner and files in its own scratch space. It never sends email, edits calendars, or acts on external systems.
9. **Fully automated capture.** No manual "send to PA" or debrief habits; they decay, and the data drifts.
10. **Eval-driven.** Each milestone is judged against a fixed eval set with known answers. A layer earns its place by improving eval results, in both instances.

## Architecture

```
Sources ──capture──▶ Inbox / landing zone ──ingest──▶ L0 raw episodes (immutable)
                                                            │
                                                            ▼
                                          Librarian (toolless LLM extraction)
                                                │                   │
                                                ▼                   ▼
                                       L1 wiki (narrative)   L2 claims graph (index)
                                                │                   │
                                                │                   ▼
              L0 + L1 as read-only files ◀──────┘     PA MCP server (domain queries)
                         │                                          │
                         └─────────────────────┬────────────────────┘
                                               ▼
                               Claude Code + agent project ◀──▶ Chat surface
                                               │
                             scheduled runs ──▶ Push channel (brief)
```

### Components

- **Capture.** Brings raw source data into an inbox (home) or landing zone (work). Raw payloads are landed as-is; normalization into episodes happens in versioned core code, not in capture logic. Capture is one-way and append-only.
  - **Home capture runs entirely on the devbox:** Gmail and iCloud Calendar via scheduled pulls, and the Obsidian vault via Obsidian's headless Sync client. The synced vault copy is outside the assistant's reach and is never written by the PA.
- **L0 raw episodes.** An append-only store with original payloads preserved alongside the normalized form. The only non-rebuildable data, so it is backed up.
- **Librarian.** Batch jobs that read new L0 episodes and produce L1 and L2 updates. LLM calls are toolless (text in, structured output out): the librarian runs with write access to the store, so its model calls have every tool disabled. Outputs are cached and keyed by episode id plus extractor version, so a rebuild re-runs only what changed. World claims are extracted only from the owner's turns in `assistant_chat` episodes; the assistant's turns are context for reading them, never a source. Telling the assistant something is a deliberate way to add it to memory: those claims count like any other source and are never suppressed, but each is marked as told to the assistant, so answers can say so.
- **L1 wiki.** LLM-maintained Markdown pages: people, topics and projects, decision logs, and a dated daily log. Claims link back to episodes. Some sections are rendered from the graph so that claims have one source of truth. On the home instance it is browsable read-only in Obsidian (a separate vault from the owner's notes).
- **L2 claims graph.** A temporal property graph used as an index for relationship and timeline questions.
- **Search.** Agentic file search (`grep` and `find` in Claude Code's shell, and Read) over L0 and L1. A search engine (full-text or hybrid) is added only when evals show it is needed.
- **PA MCP server.** Domain queries over the claims graph that file tools can't answer, plus a read-only query tool for questions they don't cover (rule 1), added in v0.12. Results are graph-shaped: nodes and edges with stable ids and the episodes behind them.
- **Assistant.** Claude Code running the shared agent project.
  - **Interactive:** sessions are driven through Remote Control at home, or Omnigent at work.
  - **Scheduled:** runs (morning brief, periodic checks) use `claude -p` or the Agent SDK against the same project.
  - **Logging:** in interactive sessions, a hook writes each exchange (an owner message and the reply) to the inbox as an `assistant_chat` episode, so facts told to the assistant flow through the librarian like any other source. Scheduled and eval sessions are not captured.
  - **Preferences:** the assistant's own preferences and persona live in the agent project and its memory files, never world facts.
- **Push channel.** One-way delivery of the brief and alerts to the owner's phone. It is per instance: a simple notifier at home, Teams via Power Automate at work.

### Assistant permissions (shared `settings.json`)

| Capability | Policy |
|---|---|
| Store (L0, L1, L2) | Read-only, enforced by the read-only mount into the VM. L0 and L1 are read as files; L2 is reached through the PA MCP server |
| Web search | Allowed |
| Web fetch | Allowed without prompting. Never an approval prompt: the chat client sets the permission mode, and the Claude app starts sessions in auto |
| Network | Whatever the VM can reach: its tailnet rules keep it off the owner's devices and LAN. An egress allowlist on the host firewall comes in v0.13, before real mail reaches the store |
| Shell and files | The normal Claude Code tools, unsandboxed inside the VM. The instructions say to write only to scratch; the VM's mounts are what make the store and everything outside the VM unwritable |
| MCP | The PA MCP server only, from v0.12: its tools are allowed, no other server may start (an MCP server allowlist, not a deny rule, since a deny would win over the PA server's allow), and claude.ai connectors are off. In v0.11, none |
| External actions | None |

- **Home hosting.** The assistant runs in a dedicated VM. It has its own Tailscale identity, access rules that keep it from reaching the owner's other devices or LAN, and snapshots before upgrades and rebuilds. The data root stays on the devbox host, where capture, ingest, and backup run; L0 is mounted into the VM read-only, and the VM's only write path back is its own inbox directory, from which ingest accepts only `assistant_chat` payloads ([ADR-0004](../adr/0004-inbox-directory-sets-source.md)). Anything running in the VM can write that directory, so a forged `assistant_chat` payload is possible. That risk is accepted while the store holds only synthetic data, and the path is closed in v0.13, before real mail reaches the store. The owner's development environment stays outside the VM.
- **Work.** The same permission file applies there, where sessions act with the owner's workspace identity.
- **Possible refinement.** A research subagent that has web access but receives only the question, never memory context.

## Data model (starter, expected to change)

### Episode envelope (L0)

| Field | Notes |
|---|---|
| `episode_id` | Deterministic and stable across re-capture. Mail uses the internet message ID, never a client item ID. Versioned items (calendar events) include a version component (change key or last-modified time), so each add, update, or delete is its own episode |
| `source` | Home: `gmail`, `icloud_calendar`, `obsidian`, `assistant_chat`. Work: `work_mail`, `work_calendar`, `work_teams_chat`, `work_meeting_teams`, `work_meeting_anarlog`, `assistant_chat` |
| `kind` | `email`, `calendar_event`, `chat`, `meeting`, `note` |
| `occurred_at` | Start and end where applicable, with timezone |
| `captured_at` | When the episode entered L0 |
| `participants` | Identifiers plus role: sender, recipient, cc, attendee, organizer, speaker, author |
| `thread_ref` | Conversation, thread, or meeting-series id |
| `calendar_event_ref` | On meetings. Multiple transcripts of one meeting are separate episodes linked to the same event; derived layers choose which to prefer |
| `body` | Normalized text. Transcripts are speaker-attributed, timestamped turns. Diarized speakers keep their labels (Speaker 1, Speaker 2); mapping labels to people is a derived step |
| `raw_ref` | Pointer to the preserved original payload |
| `content_hash`, `envelope_version` | Integrity and schema version. Unchanged periodic snapshots collapse on `content_hash` |

### Claims graph (L2)

- **Nodes:**
  - `Person`, with names, aliases, and identifiers (email addresses); the owner is one
  - `Organization`, with names, aliases, and mail domains
  - `Topic`, with a name, aliases, and a one-line description
  - `Episode`, with its source, kind, time, thread, subject, and the path of its file in L0
  - `Statement`, with kind (proposed, agreed, disagreed, asked, answered, committed, reported status, decided, or mentioned), a short summary, a quote checked against the episode's body, a timestamp, and flags for secondhand and for told to the assistant
  - `Request` and `Commitment`, with what, an optional due date, and a status: open, or how it closed (a request is fulfilled, declined, withdrawn, or accepted; a commitment is fulfilled, withdrawn, or superseded)
  - `CalendarEvent`, with its current title, start, end, location, and status (scheduled or cancelled)
- **Relationships:**
  - `SAID` (Person or Organization → Statement): the speaker
  - `RECORDED_IN` (Statement → Episode)
  - `ABOUT` (Statement or CalendarEvent → Topic)
  - `MENTIONS` (Statement → Person or Organization)
  - `PARTICIPATED_IN` (Person or Organization → Episode, with role: sender, recipient, organizer, attendee, or author)
  - `MEMBER_OF` (Person → Organization)
  - `OPENS` and `CLOSES` (Statement → Request or Commitment; a close records how)
  - `OWES` (Person or Organization → Request or Commitment) and `OWED_TO` (Request or Commitment → Person or Organization)
  - `ACCEPTED_AS` (Request → Commitment) and `SUPERSEDES` (Commitment → Commitment)
  - `VERSION_OF` (Episode → CalendarEvent, with that version's title, start, end, location, and status, and when it was made)
- **Identity.** Resolved identities are merged into one node when the graph is built, so no `SAME_AS` edges need following. Ids derive from their inputs only: the same L0 and extractor version give the same ids.
- **Later:** statement-to-statement edges (`REFERS_TO`, `RESPONDS_TO`). Extraction reads one episode at a time and can't point at another episode's statements, so these would be their own resolution step.
- **Temporal semantics.** Statements are events and accumulate. Requests, commitments, and calendar events are states: they change, and their history is kept. A person's stance on a topic is not stored: the assistant reads it from their statements in time order at query time (principle 4).
- **Canonical form.** Extraction emits node and edge records in an engine-neutral format. Each storage adapter loads them into its own engine.
  - **Home:** LadybugDB, an embedded graph database, built by our own librarian ([ADR-0005](../adr/0005-own-librarian-ladybugdb-graph.md)).
  - **Work, option one:** Amazon Neptune in Bridgestone's AWS account.
  - **Work, option two:** Delta node and edge tables, queried with SQL plus in-memory NetworkX traversal (practical at personal scale).

## Models

- **Assistant:** Claude only.
  - Home: the owner's subscription, with interactive Claude Code use through Remote Control and scheduled runs through `claude -p`.
  - Work: Databricks-served Claude through Unity Gateway.
- **Extraction:** provider-neutral through the model client. Home uses subscription CLIs (`claude -p`, Codex) with API keys as a config-level fallback. Work uses Databricks endpoints. At home the librarian's floor is Sonnet; extraction moves to Opus where evals show it pays.
- **Prompts and agent project:** shared. Model differences are caught by running the same eval set on both instances.
- **Embeddings:** local at home; a Databricks-native option at work.

## Evaluation

- **Synthetic corpus.** The fictional personal life of a fictional owner, with 6–10 people over 4–6 weeks and 3–4 storylines. It contains home-shaped raw payloads only: emails (`.eml`), calendar events and their updates (`.ics`), and daily notes (Obsidian Markdown). It is generated from a written storyline spec, then frozen and committed. The storyline spec is the ground truth. Eval questions are asked from the fictional owner's point of view at a fixed as-of time.
- **Scale corpus.** From v0.12, a superset of the synthetic corpus: its payloads unchanged, plus about six months of earlier history (roughly 1,200 episodes), new storylines, `assistant_chat` exchanges, a few adversarial emails, and the bulk mail a real inbox fills with, labeled with Gmail's categories. The original eval set's answers hold on it unchanged, and its new questions are asked at the same as-of time.
- **Work corpus (later).** A work-shaped corpus (transcripts, Teams chats, work mail) is added in the work milestones, once the real payload shapes are known.
- **Eval set.** 15–30 questions with expected answers and required evidence episode ids. Categories:
  - single-fact recall
  - attribution
  - timeline narrative
  - stance change
  - open loops and commitments
  - cross-channel synthesis
  - entity resolution
  - connection (how people, organizations, and topics relate, by paths no query anticipated)
  - paraphrase (worded unlike the sources, so a lexical search for the question's words misses)
  - abstention
- **Metrics.** Evidence recall, answer correctness (LLM judge), and citation validity, plus each answer's cost, turns, and duration.
- **Runs.** The harness drives the agent project headlessly (`claude -p` or the Agent SDK), so evals exercise the same configuration as interactive use.
- **Baselines.** Every milestone reports against the previous one. From v0.12, configurations are compared over 3 runs each on the scale corpus, and a difference counts only when it is larger than the run-to-run spread. The first baseline is agentic search over raw L0. The work instance must reach parity with home on the synthetic corpus before real work data flows. Normalizers live in core, so the work instance can ingest the home-shaped corpus even though it never captures those sources.
- **Real data.** Real-data eval questions are kept private and outside the repo, per instance.

## Repository

One monorepo with one version line. Tags mark the state of the codebase; each milestone below is labeled with the instance it targets.

```
core/          shared Python package: envelope, normalizers, ingest, extraction,
               graph schema and domain queries, wiki generation, PA MCP server
agent/         shared Claude Code project: CLAUDE.md, skills, MCP config,
               settings.json (permissions), hooks
adapters/
  home/        local storage, graph engine, CLI model client, collectors
  work/        Delta/Volumes/Lakebase storage, Databricks model client, graph adapter
deploy/
  home/        VM setup, timers, Remote Control service, push notifier
  work/        Databricks bundle, exported Power Automate flows, Omnigent/agent setup
evals/         corpus spec, frozen corpus, eval sets, harness
docs/
```

- No personal or work data is ever committed.
- The core package must install and run on Databricks (pinned, minimal dependencies; no reliance on devbox-only tooling).
- Instance-specific values (endpoints, auth, paths) live in environment configuration, never in `agent/`.

## Milestones

Each milestone ends in a working prototype that can be demonstrated, tagged in the monorepo. Home milestones come first. Work milestones begin when the owner starts at Bridgestone and may interleave with home milestones after v0.12.

### v0.10 — Foundations and baseline (home)

- Monorepo scaffold and the core package skeleton.
- Episode envelope schema, normalizers for the synthetic corpus's source shapes, and the L0 storage interface with a home adapter (append-only, idempotent ingest, raw preservation, quarantine).
- L0 backup command (restic), tested against a local repository. The off-box destination is chosen in v0.13.
- Synthetic corpus generator, frozen corpus, and eval set (personal life, home shapes).
- Model client interface with the CLI backend.
- Minimal agent project and eval harness.
- Baseline: the agent answers over raw L0 using read-only file search.

**Prototype:** run the eval set against the baseline and get a scored report.

### v0.11 — Isolated assistant (home)

- PA VM on the devbox, with its Tailscale identity and access rules.
- L0 mounted read-only into the VM and searched with file tools, as in the baseline.
- The agent project's permissions per the policy above. The fences are the VM's (read-only mount, tailnet rules, host firewall, inbox directory); inside it the assistant has its normal tools, with no Bash sandbox.
- Remote Control as a long-running service.
- Transcript hook writing `assistant_chat` episodes to the inbox.
- A paraphrase category in the eval set (questions worded unlike their sources), with the v0.10 baseline re-scored on the extended set.
- The eval set runs from inside the VM and holds the v0.10 baseline. With the fences at the VM boundary, evals of this configuration run there, not on the devbox.

**Prototype:** ask questions about the synthetic corpus from the Claude app on a phone and get cited answers.

### v0.12 — Claims graph (home)

- Spike: LadybugDB feasibility ([ADR-0005](../adr/0005-own-librarian-ladybugdb-graph.md)). A published build opens read-only in the VM (or from a copy on VM-local storage), no WAL ships in a build, the MCP server picks up new builds, the explorer runs on the host read-only, and full-text and vector indexes, the domain queries, and two open-ended questions all work.
- Scale corpus, with about 15 new questions, including connection questions. The owner reviews the storyline extension and the questions before anything is generated.
- Librarian pipeline: toolless, versioned, cached. Triage by Gmail category, extraction per episode, resolution in time order, and a fresh build published by an atomic swap. Sonnet for every call while it's developed; the scored run before merge uses Opus for extraction.
- Entity resolution: people from their identifiers, names, and aliases, and the people mentioned in bodies. Mapping diarized speakers to people waits for the first source that has them (v0.17).
- The PA MCP server in the VM, reading the current build from a read-only mount: domain queries, the schema tool, and the read-only query tool. The assistant keeps file access to L0 for evidence.
- Ladybug Explorer on the host, read-only against the current build, reachable only over Tailscale.
- Full rebuild from L0 is a single command.
- Evals compare files alone, the graph plus files, and the query tool without the domain queries, over 3 runs each, with cost, turns, and duration.

**Prototype:** on the scale corpus, the graph plus files beats files alone on timeline, attribution, open loops, and entity resolution by more than the run-to-run spread, and holds steady on the original eval set.

### v0.13 — Real personal sources (home)

- Collectors for Gmail, iCloud Calendar, and the Obsidian vault (headless Sync).
- Calendar versioning and nightly snapshot.
- Bounded backfill.
- Off-box backup destination for L0.
- An egress allowlist for the PA VM on the host firewall, in place before real mail reaches the store, grown from what the assistant fetches in use.
- The forged-exchange path closed before real mail reaches the store: nothing the assistant's own tools write can land as an `assistant_chat` episode.
- Scheduled ingest and librarian runs.
- Re-score file search on real data; add a search engine only if evidence recall drops.

**Prototype:** the assistant answers questions about the owner's real week.

### v0.14 — Wiki and daily log (home)

- L1 pages for people, topics, and decisions.
- A dated daily log.
- Sections rendered from the graph.
- Read-only Obsidian view.
- Lint pass: stale pages, contradictions, orphaned entities.
- The subgraph behind an answer, rendered as an interactive view the owner can open from the answer.

**Prototype:** browse the wiki; the assistant uses wiki, graph, and search together, and evals hold or improve.

### v0.15 — Morning brief and open loops (home)

- A scheduled headless run of a morning brief skill, delivered through the push channel. It covers today's calendar with context on attendees and topics, open commitments in both directions, and changes since yesterday.
- On-demand "what am I waiting on" and "what do I owe people" skills.

**Prototype:** a useful brief arrives every weekday morning.

### v0.16 — Work instance foundation (work)

- Core package deployed to Databricks.
- Work adapters: Delta L0 with append-only enforcement, landing-zone ingestion job, Databricks model client, job definitions, and the work graph adapter (Neptune or Delta plus NetworkX, per day-one checks).
- File access to L0 and the wiki for work sessions, as a Volumes path or an MCP read path, per day-one checks.
- Claude Code configured against Unity Gateway.
- The synthetic corpus runs end to end in the workspace.

**Prototype:** the eval set passes in Databricks at parity with home.

### v0.17 — Work capture (work)

- Power Automate flows for mail and calendar (trigger plus nightly snapshot).
- Teams transcripts for organized meetings, and Anarlog upload.
- Mapping diarized speakers to people, in entity resolution.
- Teams chat capture, by the mechanism chosen in day-one checks.
- Scheduled L0 → L1/L2 jobs.

**Prototype:** a real work week captured and queryable.

### v0.18 — Work interface (work)

- The agent project running in Omnigent on a Databricks Sandbox, or as the Agent SDK fallback app if Omnigent is unavailable.
- The morning brief run as a Databricks Job and posted to Teams through Power Automate.

**Prototype:** brief in Teams; Q&A from phone and Mac.

### Explorations (unscheduled)

- **Research subagent.** Web access isolated from memory context.
