# Personal Assistant — Architecture and Roadmap

High-level context for the PA monorepo. Specs and issues are written from this document. It sets direction and boundaries; it does not prescribe implementation.

## Purpose

A personal assistant that remembers the world around its owner (Coy): people, meetings, emails, chats, calendar, and notes. It answers questions the way a good human assistant would: with attribution, in time order, and with awareness of what is still open.

Representative questions for the work PA:

- "What's happened with the web search feature?" Expected shape: *"About a month ago you floated it in the weekly team meeting. Jay agreed and said he'd follow up with security. Two weeks ago Cam asked about it and you said you were waiting on Jay. Since then you've mentioned it in the user group, but that's as far as it's gotten."*
- "Did Cam change his mind since last week on open-source model hosting?"
- "What have I said to whom about an API key feature, and how has my stance changed?"
- "What's on my plate today, and what am I waiting on from other people?"

Representative questions for the home PA:

- "When could we fit the kids' swim lessons in, given my wife's late shifts and the birthday parties coming up?"
- "Did the contractor ever send the revised quote he promised?"
- "What did I write about the soccer league over the last month?"

The owner chats with the PA from phone and Mac, and receives a morning brief without asking.

## Two instances, one codebase

The PA runs as two fully separate instances built from this one codebase. **No data is shared between them**: work content never reaches the home PA, and personal content never reaches the work PA.

| | Home PA | Work PA |
|---|---|---|
| Hosting | Isolated VM on the owner's Ubuntu devbox, over Tailscale | Employer's Databricks workspace on AWS (Bridgestone) |
| Sources | Gmail, iCloud Calendar, Obsidian vault, assistant chat | Outlook mail and calendar, Teams chats, Teams meetings, Anarlog, assistant chat |
| Capture | Scheduled pulls by collectors on the devbox | Power Automate flows (running as the owner) landing raw payloads in a tenant landing zone; the Mac uploads Anarlog transcripts only |
| Storage | Local files and databases on the devbox | Delta tables, Unity Catalog Volumes, Lakebase |
| Jobs | systemd timers | Databricks Jobs / Lakeflow pipelines |
| Models | Claude on the owner's subscription | Databricks-served Claude through Unity Gateway's Anthropic-compatible endpoint |
| Harness | Claude Code (shared agent project) | Claude Code (shared agent project) |
| Chat | Remote Control (claude.ai/code, Claude app) | Omnigent (workspace web and mobile); fallback: Agent SDK app with a chat page |
| Brief delivery | Push channel to phone | Teams message via Power Automate |

The home PA is built first. The work instance follows once the owner starts at Bridgestone. Work-specific constraints and open questions live in the separate handoff document *Work PA on Databricks*.

### What is shared and what is swapped

**Shared core** (identical in both instances):

- **Core Python package:**
  - episode envelope, `episode_id` and `content_hash` rules, and per-source normalizers
  - L0 ingest semantics: append-only, idempotent, quarantine for malformed input
  - the librarian's deterministic steps: episode selection, the identity table, run batches, wiki lint, and `index.md` generation
- **Agent project:** a Claude Code project directory, and the assistant's entire harness configuration. It contains:
  - `CLAUDE.md` (persona and instructions)
  - `.claude/skills/` (morning brief, timelines, open loops, …)
  - `settings.json` (permissions)
  - hooks (for example, session transcripts to L0)
  - The Agent SDK reads the same project configuration, so scheduled and fallback runs behave like interactive ones.
- **Librarian project:** the librarian's Claude Code project directory: its instructions, the wiki schema, page templates, and settings. It is mounted read-only into the librarian's sandbox.
- **Eval harness, synthetic corpus, and eval sets.**

**Swapped per instance** (behind small interfaces or environment configuration):

- **Storage adapter:** L0 and wiki persistence, plus their file views: read-only to the assistant, and the wiki writable only by the librarian.
- **Job runtime:** scheduling and orchestration.
- **Model client:** "prompt plus schema in, structured output out," for the eval judge and the corpus generator. One backend uses subscription CLIs (`claude -p`, Codex); the other uses Databricks HTTP endpoints.
- **Capture:** home collectors (Python) vs. work landing-zone readers. Power Automate flow definitions are exported into the repo for versioning.
- **Harness environment:** model auth and endpoint for the assistant and the librarian, the librarian's sandbox, chat surface, and push channel.

Two rules keep the abstraction honest:

1. **Abstract at the file level.** The assistant reads L0 episodes and the wiki as files, and the librarian writes the wiki as files. Each storage adapter presents them at a path (read-only to the assistant), so nothing engine-specific is written into the agent or librarian projects. If a work session can't reach files, the work adapter adds an MCP read path; that is an adapter concern, not a change to either project.
2. **Build seams, not speculative adapters.** Define each interface when the home PA first needs it, and implement only the home adapter. The work adapters are built in the work milestones, and the shared eval set proves parity.

## Principles

1. **L0 is the only source of truth.** Raw episodes are immutable and append-only. Every other layer is derived and rebuildable from L0. Corrections are new episodes, never edits: the owner states them in chat, and the librarian applies them on its next run.
2. **The wiki is living.** The librarian maintains L1 in place, and nobody hand-edits it: fix the librarian, or add an episode. Schemas and templates start out wrong, and changing one means the librarian migrates the pages. A rebuild from L0 is for recovery only, and must stay possible.
3. **Deterministic first.** Who, when, where, and to whom come from source metadata (senders, recipients, attendees, speaker labels, timestamps), not from an LLM. The librarian reads for meaning (what happened, what was decided, what is owed); the addresses and participants in the wiki come from metadata.
4. **Precompute the index, not the answer.** Derived layers exist to find and order the right evidence. The model reads the original passages at query time and writes the answer: navigate with the wiki, answer from episodes.
5. **Provenance everywhere.** Every wiki line cites the episode it came from, and from v0.14 an external fact cites `[web:…]` with its retrieval date. Answers cite episodes, never wiki pages.
6. **The store is the product; the harness is configuration.** All PA behavior lives in the store, the agent project, and the librarian project. The harness itself contains no PA code.
7. **Contain untrusted content.** Raw source text is untrusted, since anyone can send an email, and so is everything derived from it, the wiki included. No component combines private data, untrusted content, and external communication. The fences sit at each sandbox's boundary, not inside the session:
   - The assistant's VM mounts the store read-only, its network reach is set by its tailnet rules and the host firewall, and its only write path back is its inbox directory. Inside the VM the assistant has its normal tools. From v0.13, before real mail reaches the store, it reaches only the model endpoint and has no web tools.
   - The librarian's VM can write only the wiki, reaches only the model endpoint, and has file tools only.
   - Web lookups go through an isolated research worker (v0.14) that sees neither L0 nor the wiki.

   No fence relies on an approval prompt, since the chat client sets the permission mode.
8. **Read-only toward the world.** The PA reads and remembers. Its outputs are messages to the owner and files in its own scratch space. It never sends email, edits calendars, or acts on external systems.
9. **Fully automated capture.** No manual "send to PA" or debrief habits; they decay, and the data drifts.
10. **Eval-driven.** Each milestone is judged against a fixed eval set with known answers. A layer earns its place by improving eval results, in both instances.

## Architecture

```
Sources ──capture──▶ Inbox / landing zone ──ingest──▶ L0 raw episodes (immutable)
                                                            │
                                                            ▼
                    Research worker ──answers──▶ Librarian, in its own sandbox:
                    (web only, from v0.14)       observation, consolidation,
                                                 and dreaming from v0.14
                                                            │
                                                            ▼
                                                 L1 wiki (pages, day logs)
                                                            │
                                                            ▼
                                 L0 + L1 as read-only files, and L2 search if needed
                                                            │
                                                            ▼
                                     Claude Code + agent project ◀──▶ Chat surface
                                                            │
                                          scheduled runs ──▶ Push channel (brief)
```

### Components

- **Capture.** Brings raw source data into an inbox (home) or landing zone (work). Raw payloads are landed as-is; normalization into episodes happens in versioned core code, not in capture logic. Capture is one-way and append-only.
  - **Home capture runs entirely on the devbox:** Gmail and iCloud Calendar via scheduled pulls, and the Obsidian vault via Obsidian's headless Sync client. The synced vault copy is outside the assistant's reach and is never written by the PA.
- **L0 raw episodes.** An append-only store with original payloads preserved alongside the normalized form. The only non-rebuildable data, so it is backed up.
- **Librarian.** A headless Claude Code session (`claude -p`) that keeps the wiki current, running in its own sandbox. The host picks each run's batch of new episodes deterministically (by Gmail category, a daily note's latest version, and a chat's owner turns as the evidence) and tells the session what "now" is. A run has two phases:
  - **Observation** writes one observation per relevant episode into the day log for that episode's day, linking people, organizations, and topics by slug. It never creates pages.
  - **Consolidation** folds the run's new observations into pages (current state, decisions, open loops). It creates a page once a slug has been linked on 3 distinct days (a placeholder evals tune) or appears in a decision or loop line, after checking aliases, addresses, and near-duplicate slugs.

  Most episodes change no page. In `assistant_chat` episodes only the owner's turns are evidence; the assistant's turns are context for reading them. Telling the assistant something is a deliberate way to add it to memory, and a correction ("Okie is Ben Okafor") is applied on the next run: pages merged, aliases added, links rewritten. Around the sessions, the host does everything deterministic: the batch, the identity table (addresses grouped by display name, from source metadata), lint, `index.md`, and one git commit per run, so `git revert` undoes any run. From v0.14, dreaming is a separate, periodic run over the whole wiki.
  - **Fences.** L0 and the librarian project are mounted read-only, and the wiki is the only writable mount; its git directory stays outside the mount. The session has file tools only: no shell, no web tools, no MCP, and no network beyond the model endpoint. It holds private data and reads untrusted content, so external communication would complete the lethal trifecta, and because it writes memory, injected text would persist. External facts it needs become "needs lookup" markers until the research worker exists.
- **L1 wiki.** Markdown pages for people, organizations, and topics, plus a day log per day, maintained in place by the librarian (principle 2). Every line cites an episode. Pages hold identity (aliases and addresses), current state, decisions, and open loops; day logs are the timeline, and a page's backlinks are its history. A generated `index.md` orients. The owner views the wiki read-only in Obsidian, as one-way copies on Mac and phone. The layout and line formats are under the data model.
- **Search.** Agentic file search (`grep` and `find` in Claude Code's shell, and Read) over L0 and L1, starting from `index.md`. An L2 search index (full-text or hybrid; QMD is the candidate) is added only when evals show paraphrase misses. It is derived and safe to delete.
- **Research worker (v0.14).** Web search, with no L0 or wiki mount. It takes validated public questions (length-capped, with no URLs, email addresses, or names and aliases from the wiki) and returns structured answers, which the librarian records as `[web:…]` facts with retrieval dates.
- **Assistant.** Claude Code running the shared agent project.
  - **Interactive:** sessions are driven through Remote Control at home, or Omnigent at work.
  - **Scheduled:** runs (morning brief, periodic checks) use `claude -p` or the Agent SDK against the same project.
  - **Answering:** navigate with the wiki, answer from episodes. The assistant reads `index.md` and pages, widens its searches with aliases and addresses, opens the episodes, and answers from them, citing `[ep:…]`, never a page. The wiki is built from untrusted mail and can be wrong, and its lists are never exhaustive.
  - **Logging:** in interactive sessions, a hook writes each exchange (an owner message and the reply) to the inbox as an `assistant_chat` episode, so what the owner tells the assistant, corrections included, reaches the librarian like any other source. Scheduled and eval sessions are not captured.
  - **Preferences:** the assistant's own preferences and persona live in the agent project, never in the wiki.
- **Push channel.** One-way delivery of the brief and alerts to the owner's phone. It is per instance: a simple notifier at home, Teams via Power Automate at work.

### Assistant permissions (shared `settings.json`)

| Capability | Policy |
|---|---|
| Store (L0, L1, L2) | Read-only, enforced by the read-only mounts into the VM. L0 and the wiki are read as files |
| Web search | Allowed while the store is synthetic; denied from v0.13 (principle 7) |
| Web fetch | Allowed without prompting while the store is synthetic; denied from v0.13. Never an approval prompt: the chat client sets the permission mode, and the Claude app starts sessions in auto |
| Network | Whatever the VM can reach: its tailnet rules keep it off the owner's devices and LAN. From v0.13, before real mail reaches the store, the host firewall limits it to the model endpoint |
| Shell and files | The normal Claude Code tools, unsandboxed inside the VM. The instructions say to write only to scratch; the VM's mounts are what make the store and everything outside the VM unwritable |
| MCP | None: no servers configured, claude.ai connectors off, every MCP tool denied |
| Memory | Claude Code's auto memory is off from v0.13, so injected text can't carry over from one session to the next |
| External actions | None |

- **Home hosting.** The assistant runs in a dedicated VM. It has its own Tailscale identity, access rules that keep it from reaching the owner's other devices or LAN, and snapshots before upgrades and rebuilds. The data root stays on the devbox host, where capture, ingest, and backup run; L0 and the wiki are mounted into the VM read-only, and the VM's only write path back is its own inbox directory, from which ingest accepts only `assistant_chat` payloads ([ADR-0004](../adr/0004-inbox-directory-sets-source.md)). Anything running in the VM can write that directory, so a forged `assistant_chat` payload is possible. That risk is accepted while the store holds only synthetic data, and the path is closed in v0.13, before real mail reaches the store. The owner's development environment stays outside the VM.
- **Librarian sandbox (home).** The librarian runs in its own Incus VM, started for runs and stopped otherwise ([ADR-0007](../adr/0007-living-wiki-fenced-librarian.md)). It has no Tailscale identity, and the host firewall limits it to the model endpoint. Managed settings deny it the shell, web tools, and MCP in every permission mode, auto memory is off, and its auth is a setup token that can make model requests only. L0 and the librarian project are mounted read-only and the wiki read-write; the wiki's git directory stays on the host, which commits each run.
- **Work.** The same permission file applies there, where sessions act with the owner's workspace identity. The librarian's fences are re-derived for Databricks in v0.16.

## Data model (starter, expected to change)

### Episode envelope (L0)

| Field | Notes |
|---|---|
| `episode_id` | Deterministic and stable across re-capture. Mail uses the internet message ID, never a client item ID. Versioned items (calendar events) include a version component (change key or last-modified time), so each add, update, or delete is its own episode |
| `source` | Home: `gmail`, `icloud_calendar`, `obsidian`, `assistant_chat`. Work: `work_mail`, `work_calendar`, `work_teams_chat`, `work_meeting_teams`, `work_meeting_anarlog`, `assistant_chat` |
| `kind` | `email`, `calendar_event`, `chat`, `meeting`, `note` |
| `occurred_at` | Start and end where applicable, with timezone |
| `captured_at` | When the episode entered L0 |
| `participants` | Identifiers plus role: sender, recipient, cc, attendee, organizer, speaker, author |
| `thread_ref` | Conversation, thread, or meeting-series id |
| `calendar_event_ref` | On meetings. Multiple transcripts of one meeting are separate episodes linked to the same event; derived layers choose which to prefer |
| `body` | Normalized text. Transcripts are speaker-attributed, timestamped turns. Diarized speakers keep their labels (Speaker 1, Speaker 2); mapping labels to people is a derived step |
| `raw_ref` | Pointer to the preserved original payload |
| `content_hash`, `envelope_version` | Integrity and schema version. Unchanged periodic snapshots collapse on `content_hash` |

### Wiki (L1)

```text
<data root>/
├── l0/          immutable episodes; read-only to every agent
├── wiki/        L1: the librarian's only writable mount; opened read-only in Obsidian
│   ├── index.md   generated from each page's summary
│   ├── days/      day logs, YYYY-MM-DD.md
│   ├── people/
│   ├── orgs/
│   └── topics/
├── wiki.git/    the wiki's git directory, on the host only: one commit per run
└── search/      L2, optional: a derived index, safe to delete
```

| Need | Representation | Written by |
|---|---|---|
| Identity | `aliases:` (and `emails:` for people) in page frontmatter | Librarian, from the identity table's source metadata first |
| Decision state | Dated decision lines with a stance, superseded in place | Librarian |
| Open loops | Checkbox lines on the page they belong to: owed by → owed to, asked or promised, with an optional due date | Librarian |
| Absence ("haven't heard back") | Per-source sync watermarks (v0.13) | Collectors |
| History and timeline | Day logs; a page's backlinks are its timeline | Librarian (observation) |
| Orientation | Generated `index.md`, plus "Current state" on each page | Host; librarian |
| Relationships | Wikilinks between pages, seen in Obsidian's graph view | Librarian |
| Operations log | One git commit per run, with a structured message | Host |

Pages have a fixed skeleton and free content. The librarian project's templates set the page types (person, organization, and topic, plus the day log), the required frontmatter (`type`, `aliases`, `status`, `summary`, `updated`, plus `emails` for people), the section names, and strict formats for observation, decision, and loop lines, since grep and lint parse them. "Current state" and "Notes" are free-form.

```markdown
---
type: topic
aliases: [X chat, the new chat app]
status: active
summary: Company X's pilot chat app; web search provider pending security review.
updated: 2026-10-18
---
# X chat

## Current state
Pilot in progress. The web search provider is pending a security review.

## Decisions
- 2026-10-16 · Web search provider: proposed Perplexity (me) [ep:2026-10-16-x-chat-sync]
- ~~2026-09-30 · Hosting: decided Azure (me)~~ superseded 2026-10-09 by Databricks [ep:2026-10-09-arch-review]

## Open loops
- [ ] [[jay]] → me: confirm Perplexity is an approved vendor · promised 2026-10-16 [ep:2026-10-16-x-chat-sync]

## Notes
```

Line formats, as a starting point the v0.12.1 spec finalizes (the IDs above are placeholders):

- **Observation:** `- <one line> [[slug]] … [ep:<id>]`, in the day log for the episode's day, linking people, organizations, and topics by slug whether or not they have a page yet.
- **Decision:** `- YYYY-MM-DD · <subject>: <proposed|decided|rejected> <choice> (<who>) [ep:<id>]`. A superseded line is struck through and gains `superseded YYYY-MM-DD by <choice> [ep:<id>]`.
- **Loop:** `- [ ] <owed by> → <owed to>: <what> · <asked|promised> YYYY-MM-DD [· due YYYY-MM-DD] [ep:<id>]`, closed in place as `- [x] … · closed YYYY-MM-DD [ep:<id>]`. "Asked" means the party owed asked; "promised" means the party owing promised. The owner is written `me`, so `rg '^- \[ \] .*→ me:'` lists what the owner is waiting on, and `rg '^- \[ \] me → .*· promised'` what they've promised. Each loop has one home: its topic's page, or else the other party's.
- **Citations** stay plain `[ep:…]` IDs, never wikilinks, so the graph view shows only people, organizations, topics, and day logs.

## Models

- **Assistant:** Claude only.
  - Home: the owner's subscription, with interactive Claude Code use through Remote Control and scheduled runs through `claude -p`.
  - Work: Databricks-served Claude through Unity Gateway.
- **Librarian:** a headless Claude Code session: `claude -p` on the subscription at home, Databricks-served Claude at work. It starts on Opus 5.5 at medium effort, which extracted better than Sonnet in v0.12 at about the same cost per answer; evals tune it from there.
- **Eval judge and corpus generator:** provider-neutral through the model client. Home uses subscription CLIs (`claude -p`, Codex) with API keys as a config-level fallback. Work uses Databricks endpoints.
- **Prompts, the agent project, and the librarian project:** shared. Model differences are caught by running the same eval set on both instances.
- **Embeddings:** only if a search index is added: local at home, a Databricks-native option at work.

## Evaluation

- **Synthetic corpus.** The fictional personal life of a fictional owner, with 6–10 people over 4–6 weeks and 3–4 storylines. It contains home-shaped raw payloads only: emails (`.eml`), calendar events and their updates (`.ics`), and daily notes (Obsidian Markdown). It is generated from a written storyline spec, then frozen and committed. The storyline spec is the ground truth. Eval questions are asked from the fictional owner's point of view at a fixed as-of time.
- **Scale corpus.** From v0.12, a superset of the synthetic corpus: its payloads unchanged, plus about six months of earlier history (roughly 1,200 episodes), new storylines, `assistant_chat` exchanges, a few adversarial emails, and the bulk mail a real inbox fills with, labeled with Gmail's categories. The original eval set's answers hold on it unchanged, and its new questions are asked at the same as-of time.
- **Work corpus (later).** A work-shaped corpus (transcripts, Teams chats, work mail) is added in the work milestones, once the real payload shapes are known.
- **Eval set.** 15–30 questions with expected answers and required evidence episode ids. Categories:
  - single-fact recall
  - attribution
  - timeline narrative
  - stance change
  - open loops and commitments
  - cross-channel synthesis
  - entity resolution
  - connection (how people, organizations, and topics relate, by paths no query anticipated)
  - paraphrase (worded unlike the sources, so a lexical search for the question's words misses)
  - where things stand (a topic's current state, its decisions, and what's still open; from v0.12.1)
  - abstention
- **Metrics.** Evidence recall, answer correctness (LLM judge), and citation validity, plus each answer's cost, turns, and duration. From v0.12.1, each answer's tool calls are recorded too, with the share of its cited episodes the session actually opened.
- **Runs.** The harness drives the agent project headlessly (`claude -p` or the Agent SDK), so evals exercise the same configuration as interactive use.
- **Configurations.** Files alone, and from v0.12.1 files plus wiki. Search engine configurations come only if one is added.
- **Eval wikis.** A files-plus-wiki run reads a wiki built by replaying the frozen corpus through the librarian in weekly batches, each told its batch's end as "now". It is built once per librarian version (a hash of the librarian project, model, and effort) and reused by every eval run of that version. A replay resumes after a failure and records its cost, and the final wiki and its run log are committed beside the results. Development iterates on Argus; the scale corpus is replayed for scored comparisons. Web lookups stay off in evals: they'd leak the real date and contradict the fictional storyline.
- **Injection checks** cover the librarian as well as the assistant: in an eval wiki, an adversarial episode may be cited only by observations, never by a decision, a loop, an alias, an address, or a page.
- **Baselines.** Every milestone reports against the previous one. From v0.12, configurations are compared over 3 runs each on the scale corpus, and a difference counts only when it is larger than the run-to-run spread. The first baseline is agentic search over raw L0. The work instance must reach parity with home on the synthetic corpus before real work data flows. Normalizers live in core, so the work instance can ingest the home-shaped corpus even though it never captures those sources.
- **Real data.** Real-data eval questions are kept private and outside the repo, per instance. The home set starts in v0.13, and it gives the wiki its real verdict.

- No personal or work data is ever committed.

- Instance-specific values (endpoints, auth, paths) live in environment configuration, never in `agent/` or `librarian/`.

## Milestones

Each milestone ends in a working prototype that can be demonstrated, tagged in the monorepo. Home milestones come first. Work milestones begin when the owner starts at Bridgestone and may interleave with home milestones after v0.12.

### v0.10 — Foundations and baseline (home)

- Monorepo scaffold and the core package skeleton.
- Episode envelope schema, normalizers for the synthetic corpus's source shapes, and the L0 storage interface with a home adapter (append-only, idempotent ingest, raw preservation, quarantine).
- L0 backup command (restic), tested against a local repository. The off-box destination is chosen in v0.13.
- Synthetic corpus generator, frozen corpus, and eval set (personal life, home shapes).
- Model client interface with the CLI backend.
- Minimal agent project and eval harness.
- Baseline: the agent answers over raw L0 using read-only file search.

**Prototype:** run the eval set against the baseline and get a scored report.

### v0.11 — Isolated assistant (home)

- PA VM on the devbox, with its Tailscale identity and access rules.
- L0 mounted read-only into the VM and searched with file tools, as in the baseline.
- The agent project's permissions per the policy above. The fences are the VM's (read-only mount, tailnet rules, host firewall, inbox directory); inside it the assistant has its normal tools, with no Bash sandbox.
- Remote Control as a long-running service.
- Transcript hook writing `assistant_chat` episodes to the inbox.
- A paraphrase category in the eval set (questions worded unlike their sources), with the v0.10 baseline re-scored on the extended set.
- The eval set runs from inside the VM and holds the v0.10 baseline. With the fences at the VM boundary, evals of this configuration run there, not on the devbox.

**Prototype:** ask questions about the synthetic corpus from the Claude app on a phone and get cited answers.

### v0.12 — Claims graph (home)

- Spike: LadybugDB feasibility ([ADR-0005](../adr/0005-own-librarian-ladybugdb-graph.md)). A published build opens read-only in the VM (or from a copy on VM-local storage), no WAL ships in a build, the MCP server picks up new builds, the explorer runs on the host read-only, and full-text and vector indexes, the domain queries, and two open-ended questions all work.
- Scale corpus, with about 15 new questions, including connection questions. The owner reviews the storyline extension and the questions before anything is generated.
- Librarian pipeline: toolless, versioned, cached. Triage by Gmail category, extraction per episode, resolution in time order, and a fresh build published by an atomic swap. Sonnet for every call while it's developed; the scored run before merge uses Opus for extraction.
- Entity resolution: people from their identifiers, names, and aliases, and the people mentioned in bodies. Mapping diarized speakers to people waits for the first source that has them (v0.17).
- The PA MCP server in the VM, reading the current build from a read-only mount: domain queries, the schema tool, and the read-only query tool. The assistant keeps file access to L0 for evidence.
- Ladybug Explorer on the host, read-only against the current build, reachable only over Tailscale.
- Full rebuild from L0 is a single command.
- Evals compare files alone, the graph plus files, and the query tool without the domain queries, over 3 runs each, with cost, turns, and duration.

**Prototype:** on the scale corpus, the graph plus files beats files alone on timeline, attribution, open loops, and entity resolution by more than the run-to-run spread, and holds steady on the original eval set.

**Not met.** Files alone scored higher, so the claims graph was removed and the assistant answers from files until the wiki milestone ([ADR-0006](../adr/0006-remove-the-claims-graph.md), [verdict](../../evals/baselines/v0.12/verdict.md)). The eval work and the Captured-At contract were kept.

### v0.12.1 — Wiki memory (home)

- Spike: the librarian's sandbox ([ADR-0007](../adr/0007-living-wiki-fenced-librarian.md)). In its own Incus VM, `claude -p` works with egress limited to the model endpoint; the shell, web tools, and MCP stay denied whatever flags are passed; nothing written into the wiki loads as configuration; and the wiki's git directory is out of reach.
- The librarian project: instructions, the wiki schema, and templates for person, organization, and topic pages and the day log.
- The librarian in its VM, started by hand on the host (`pa librarian run`, and `pa librarian replay` for rebuilds and eval wikis): observation into day logs, then consolidation into pages, with the page threshold, the alias, address, and near-duplicate checks, and "needs lookup" markers.
- An identity table from source metadata, ported from v0.12's deterministic resolution: addresses grouped by exact display name, organizations by mail domain, and mail from the owner's address without the Sent label flagged as forged.
- Deterministic lint. Errors (files outside the layout, bad frontmatter or lines, citations of episodes not in L0, addresses not in L0 or on two pages) fail a run after two fix attempts. Warnings (orphans, loops past due or long open, duplicate candidates, slugs over the threshold, "needs lookup" markers) go into the commit message. `index.md` is generated from page summaries.
- The assistant navigates with the wiki and answers from episodes, with the wiki as a third read-only share in its VM.
- Owner corrections from chat, applied on the next run.
- The live data root reseeded with the scale corpus, and its wiki seeded from the scale eval wiki.
- A read-only Obsidian view on Mac and phone, by one-way pulls over the tailnet.
- Evals: files alone vs. files plus wiki on the scale corpus (3 runs each) and Argus (1 run). Six new questions, reviewed by the owner: an overdue sweep, a pending-decisions sweep, and four in a new "where things stand" category; files alone is re-run on the grown set as the baseline. The assistant's tool calls are recorded, and injection checks cover the librarian.

**Prototype:** on the scale corpus with the new questions, files plus wiki scores at least as well as files alone overall and on open loops, entity resolution, and where things stand, and no category drops by more than the run-to-run spread. It holds on Argus, and citation validity doesn't drop. From the phone, the assistant answers with the wiki's help, and a correction made there shows up in the wiki after the next run.

### v0.14 — Dreaming and research (home)

- Dreaming: the librarian's periodic review of the whole wiki, on its own schedule in the same VM. Lint flags candidates mechanically, and dreaming judges them: which duplicate candidates are one person, organization, or topic; where a page's current state contradicts its decisions; whether a stale loop actually closed; which recurring notes deserve a template section; and which external facts are due for a re-check before a deadline that depends on them.
- Apply or propose: when a careful re-read of L0 settles it, the librarian applies the fix (revertible with git); when it needs the owner's knowledge, it becomes a proposal.
- A proposals review file.
- The research worker: web search, with no L0 or wiki mount. It takes validated public questions (length-capped, with no URLs, email addresses, or names and aliases from the wiki) and returns structured answers, which the librarian records as `[web:…]` facts with retrieval dates.

**Prototype:** to be defined in the v0.14 spec.
